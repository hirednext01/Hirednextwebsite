## Ordered operations

1. `inspect`: verify `service=rebuild_1799`, recipient, amount and reference. Stop on completed/active ownership or an unresolved send. Read `fulfilment`, not just the HTTP status. Tests are jobs-only, zero-value fixtures and never commercial demand or revenue.
2. `confirm_owner`: exact INR 1,799, reference and authentic owner confirmation, using the existing proof format. Accept Taru's prior exact confirmation without asking again. Do not spend time rebuilding payments. If genuinely missing, ask once. `confirm_test` with `type=internal_test`, amount 0 is restricted to internal fixtures.
3. `source`: obtain original bytes, hash and extracted text. Extract locally if needed, without a paid fallback. For unreadable files ask the customer for readable text in the service thread; retain the original. Do not change the order file silently.
4. `intake`: send `source_sha256`, `source_text` only if server extraction is empty, and 1–10 `questions`, each `{question, why, source_quote}`. Focus on the few missing details materially affecting this CV: target, scope, authority, dates or supported achievements. Quotes must literally occur in the original. Never demand invented metrics. The email also offers Classic, Modern and Leadership directions, asks for two choices or permission for the system to choose, and states the deliverables and two revision rounds. Repeating intake is a no-op.
5. Customer reply: fetch the genuine Gmail message and verify its sender against the canonical order. Exclude jobs copies, bounces and automated messages. When usable answers arrive, call `answers` with `gmail_message_id`, `sender_email`, exact relevant `text`, and optionally `templates`, exactly two distinct keys from `ats_classic`, `ats_modern`, `executive_ats`. Retain genuine candidate wording; don't turn hypotheses into facts. Do not treat a thank-you, quoted question or marketing footer as a new answer. If a key detail is still unclear, ask the candidate once in the same thread; nonessential unavailable figures can be omitted. Replayed Gmail IDs cannot duplicate evidence. Customer refusal to supply a metric is a valid answer.
6. `claim`: after usable answers. Returns one-hour `lease`, exact `delivery_id`, and state containing `source_sha256`, `answers_sha256`, selected templates and round. Stop on `already_processing`, `existing_delivery_owner`, `already_delivered` or `paused`. Use the canonical original plus recorded answers; `source` also returns the previous bundle on a revision.
7. Write two complete CVs with different emphasis/wording and the selected designs. Preserve every employer, actual title, date, qualification and number. A target title must be labelled as a target if not a role already held. No invented budget, responsibility, credential, software or job promise. Ask the candidate about contradictions. Preserve clear company spacing, readable type and conventional linear sections. No haze, large boxes or fake template rankings. Photos are optional only when explicitly supplied/appropriate; this automated text path does not fabricate one.
8. Render locally with `scripts/render_cv_rebuild.py` (also fetch `scripts/render_cv_assessment.py`). Inspect all PDF pages and extracted text. Verify unsupported numbers, chronology, names, canonical email/phone, page breaks, spacing and variant differences. Set quality flags only after the checks. Use no paid AI API. Each CV must fit within 1–4 readable pages. The initial packet also includes the three-page assessment of the original CV; label that scope clearly when the rebuild uses additional answers. Revisions retain the original assessment and send updated CVs only.
9. `deliver`: send `lease`, `transport:"gmail"` and `bundle` below. The website validates evidence, hashes, selected templates, distinct content and PDFs; creates the two Word counterparts from the same content; privately retains every version; reserves one packet for the connected jobs sender above. Reconciliation saves existing CV Studio documents and the order record. Initial packet: five files (two PDF CVs, two DOCX CVs, one assessment PDF). Revision packet: four files. Send the reserved packet once.
10. Verify the actual jobs copy, exact stage reference, canonical recipient and all attachment byte counts/SHA-256 against the returned receipt. Use authorised Gmail raw MIME decoding if attachment download is unavailable. Parse PDFs and the DOCX ZIP/XML. Email arrival alone is insufficient. For uncertain SMTP, inspect `pending`, then call `reconcile` only with a genuine matching `gmail_message_id`, `recipient` and `stage_id`, after verifying attachment bytes. Never replay an uncertain send. Only unresolved recovery needs Taru.

## Bundle contract

`bundle` fields: exact `candidate_name`, `candidate_email`, `candidate_phone`, `source_sha256`, `answers_sha256`, `delivery_id`; `source_text` extracted from original; integer `external_api_cost_inr:0`; `quality:{facts_checked:true,no_invented_claims:true,layout_checked:true}`; exactly two `variants`.

Each variant: `template_key`, `explanation` (how this version differs, at least 30 characters), `source_quotes` (literal supporting quotes from original/recorded answers), `content`, and `pdf_base64` added by the renderer. Content uses `target_title`, `summary`, `core_skills` array, `experience` array of `{company,title,location?,dates,bullets:[...]}`, optional `selected_achievements`, `education`, `certifications`, `tools`, `board_highlights` arrays, and empty `clarifications`. Every numeric literal must be evidenced, including dates; don't use decorative years or unrelated numeric quality notes. Omit absent optional facts, not placeholder strings. The two content objects must differ substantively.

On round 0 include `assessment:{report,pdf_base64}` using the assessment contract and exact delivery ID `<rebuild delivery_id>-ASSESSMENT`. The source hash remains the original file hash. The renderer binds canonical contacts, template, order/round, original hash, answer hash and full structured content into each PDF's metadata digest. Never change content after rendering; rerender if it changes. Use `tests/fixtures/cv_automation_rebuild.json` only for schema/fictional QA, never as a real customer's output.

## Revisions, reminders and pause

Stable subject: `Your HiredNext CV Rebuild | HN-CV-REBUILD-UPGRADE-<id>` (or ASSESSMENT for direct lead orders). Stage IDs end in `-INTAKE`, `-REMINDER-1/2`, `-R0`, `-R1`, `-R2`. Use the subject and actual order identity; never infer a recipient from an arbitrary forwarded subject.

After delivery, a genuine change request uses `request_revision` with authentic reply provenance and optional new template choices. Round 1 and round 2 are included; the server rejects a third. Each round opens a new lease and preserves prior bundles, PDFs, Word files, email receipts and CV Studio versions. Read the previous bundle and apply the requested changes without losing valid facts. Do not count a thank-you or repeated message as a revision. After two rounds explain the included scope using existing terms; don't invent a paid add-on or promise free extra rounds.

For a genuine customer pause/resume, `pause` / `resume` accept the same reply fields. A paused order cannot be claimed or reminded. These actions are recorded without generating another email; answer briefly in the existing thread if needed. No reply should be sent to an automatic jobs copy.

Operations Control owns the existing daily sweep, not a new scheduler. Inspect only new/pending rebuild alerts from the last 14 days, dedupe canonical orders and skip tests/historic owners. `remind` with `transport:"gmail"` is server-gated: awaiting answers only, at most two reminders, first after 24h and second after 72h from intake. Stop after answers, pause, delivery or the second reminder. The website journal is authoritative; send only its reserved outbound using the verified sender contract, never independently drafted reminders. Inspect recently ready/expired-lease orders for recovery using this same worker contract; avoid active claims. No routine founder notification.

Unresolved exceptions: exact missing confirmation, conflicting facts the customer cannot resolve, expired access, exhausted task capacity, or failed delivery after bounded reconciliation. Log via `exception` with a machine-readable code, keep the order and original intact, and notify Taru once only when her action is needed. Record receipts and costs independently. Internal tests and interest are not revenue; profit and earnings remain unknown without real receipts and costs.
